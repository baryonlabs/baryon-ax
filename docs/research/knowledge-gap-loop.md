## 0. 요약

> "답 못 할 질문"은 실패가 아니라 **아직 수집하지 않은 데이터의 목록**이다.

Baryon AX는 근거를 찾지 못한 답변을 버리지 않고 **지식 공백(knowledge gap)** 으로 기록한다. 관리자는 공백을 검토해 **온톨로지 꾸러미 초안**으로 승격하고, 그 꾸러미가 요구하는 소스(문서·DB)를 채운 뒤 같은 질문으로 **재검증**한다. 이 루프가 닫히면 같은 유형의 질문은 다음부터 근거와 함께 답한다.

현재 구현 범위는 **감지 → 저장 → 클러스터링 → 꾸러미 초안 → 관리자 승인 → (소스 유입 시) 자동 재검증 → 해결** 까지다. 재검증은 수동 API와 소스 업로드 시 자동 트리거를 모두 지원한다.

## 1. 아이디어의 재정의

"답 못 할 질문을 걸러낸다"는 두 가지로 해석할 수 있고, 둘 다 필요하다.

| 해석 | 목적 | 현재 상태 |
| --- | --- | --- |
| **사전 필터** — 답하기 전에 "이건 답할 수 없다"고 판정 | 환각 방지, 비용 절감, 안전한 거절 | 🔶 프롬프트 수준(근거 없으면 거절). 명시적 answerability gate는 P1 |
| **사후 수집** — 답한 뒤 근거 부족을 감지해 기록 | 데이터 요구사항 발굴, 개선 루프 | ✅ 구현 + 자동 재검증 |

핵심은 **거절 자체가 아니라 거절의 축적**이다. 거절만 하고 버리면 같은 질문이 영원히 반복된다. 그래서 Baryon AX는 거절/모호/무근거 응답을 **질문·사유·용어·발생 횟수**로 남긴다.

### 1.1 4단계 루프

```text
① 감지 (Detect)
   응답 후: 출처 0 / 거절 표현 / 모호 표현 / 빈 답변
        │
        ▼
② 분류 (Triage)
   왜 답을 못 했는가?  데이터 없음 / 검색 실패 / 권한 / 질문 모호 / 모델 문제
        │
        ▼
③ 요구사항화 (Specify)
   반복 용어 클러스터 → 엔티티·관계·필요 소스·수용 질문을 담은 꾸러미 초안
        │
        ▼
④ 재검증 (Close the loop)
   소스 수집 → 재색인 → 같은 질문 재평가 → 커버리지 상승 확인
```

현재 ①③④의 앞부분(초안 생성)까지 자동화했고, ②는 부분 자동(사유 기록)·부분 수동(관리자 판단), ④는 수동이다.

## 2. 처리 근거 — 왜 이렇게 설계했는가

| 설계 결정 | 근거 |
| --- | --- |
| **응답 후 감지** | 스트리밍 응답을 막지 않고, 실제 답변 내용(거절·모호 표현)을 근거로 삼기 위해 |
| **규칙 기반 감지** | 결정론적·설명 가능·추가 추론 비용 0. 감사와 재현이 가능해야 관리자 검토가 성립 |
| **임베딩 없는 클러스터링** | Basic Core는 Qdrant가 꺼져 있을 수 있음. TF×IDF 용어 겹침은 의존성 없이 동작 |
| **JSONL 저장** | 감사 로그와 동일한 append-only 패턴. 장애 시 부분 기록 보존, Postgres 없이 동작 |
| **관리자 승인 필수** | 자동으로 온톨로지를 만들면 잘못된 개념이 지식이 된다. 초안(draft)과 승인을 분리 |
| **조직 스코프** | 질문에는 고객사·부서 정보가 섞인다. 다른 조직의 공백이 보이면 정보 누출 |
| **감사 이벤트** | `knowledge.gap_detected`, `knowledge.gap_dismissed`, `ontology.pack_created` — 누가 무엇을 승인했는지 추적 |
| **NDF/NFC 정규화** | 실제로 "답 못 함"의 원인이 데이터 부족이 아니라 인코딩 불일치였다(§6). 감지와 원인 분류를 분리해야 하는 이유 |

## 3. 현재 구현 — 무엇이 어떻게 동작하나

### 3.1 구성 요소

| 계층 | 구현 | 역할 |
| --- | --- | --- |
| 감지 | `gaps.detect_reasons()` | 응답·출처 수로 사유 판정 |
| 저장 | `GapStore` (JSONL) | 중복 집계, 상태 전이, 조직 스코프 |
| 클러스터 | `gaps.cluster_gaps()` | 용어 가중치로 질문 묶음 |
| 꾸러미 | `gaps.build_pack()`, `PackStore` | 엔티티·관계·소스·수용 질문 초안 |
| API | `/v1/admin/gaps*`, `/v1/admin/ontology-packs*` | 관리자 조회·제외·승인 |
| UI | 웹 "지식 공백" 뷰 | 요약·클러스터·공백 목록·꾸러미 |
| 감사 | `knowledge.gap_*`, `ontology.pack_created` | 거버넌스 추적 |

### 3.2 감지 사유

응답 후 다음 신호를 평가한다(`detect_reasons`).

| 사유 | 조건 | 의미 |
| --- | --- | --- |
| `no_citations` | 검색을 켰는데 출처 0건 | 색인에 근거가 없거나 검색이 실패 |
| `refusal` | 거절 표현 포함 ("찾을 수 없", "확인할 수 없", "couldn't find" 등) | 모델이 근거 부족을 인정 |
| `vague` | 모호 표현 포함 ("아마", "것 같", "maybe", "possibly" 등) | 근거 없이 추정 |
| `empty_answer` | 답변이 공백 | 모델·프롬프트 오류 |

> 거절 표현이 하나라도 있으면 모호 표현보다 우선한다(`elif`). 둘 다 기록하지 않아 사유가 중복되지 않는다.

### 3.3 중복 집계

- 키: `sha1(organization_id + normalized_question)`
- 같은 질문이 다시 들어오면 새 레코드를 만들지 않고 `occurrences += 1`, `last_seen` 갱신, 사유 합집합
- `dismissed` 상태였는데 다시 발생하면 `open`으로 복귀 → "중요하지 않다"고 판단한 질문도 반복되면 다시 검토 대상

### 3.4 클러스터링

1. 질문에서 한글/영문 용어 추출, 조사 제거, 불용어 제거
2. 가중치 `tf × (1 + log((N+1)/(df+0.5)))`
3. 각 질문의 상위 5개 용어 집합 비교
4. **2개 이상 겹치거나**, 1개라도 전체 공백의 30% 이하에서만 등장하는 희소 용어면 병합
5. 클러스터 라벨 = 가중치 합 1위 용어, 꾸러미 이름 = `"<라벨> 온톨로지"`

### 3.5 꾸러미 초안

```json
{
  "schema_version": 1,
  "id": "ont_...",
  "organization_id": "org",
  "name": "인건비 온톨로지",
  "domain": "인건비",
  "status": "draft",
  "source_gap_ids": ["gap_..."],
  "source_questions": ["2027년 계약 갱신 일정은?"],
  "entities": [{"name": "인건비", "type": "concept", "synonyms": [], "source": "knowledge_gap"}],
  "relations": [{"from": "인건비", "type": "related_to", "to": "예산", "confidence": "candidate"}],
  "required_sources": [{"kind": "system", "hint": "HR 시스템, 인사 규정 문서"}],
  "acceptance_questions": ["인건비 예산 편성 기준은?"],
  "notes": "자동 생성된 초안입니다. 관리자 검토 후 ..."
}
```

- `entities`는 공백 용어에서, `relations`는 인접 용어 후보로 만든다. **확정이 아니라 후보**다.
- `required_sources`는 규칙 기반 힌트다. 키워드 구체성(문자 길이)으로 순위를 정해, "인건비 예산"은 HR을 먼저, ERP를 두 번째로 제안한다.
- `acceptance_questions`는 나중에 **재검증 질문 세트**로 그대로 쓰기 위해 저장한다.

### 3.6 API

| 메서드 | 경로 | 동작 |
| --- | --- | --- |
| `GET` | `/v1/admin/gaps?status=open\|all&limit=` | 공백 목록 + 사유 요약 |
| `POST` | `/v1/admin/gaps/{id}/dismiss` | 검토 제외 |
| `GET` | `/v1/admin/gaps/clusters` | 열린 공백의 클러스터 제안 |
| `POST` | `/v1/admin/ontology-packs` | 선택 공백 → 꾸러미 초안 저장, 공백을 `converted`로 |
| `GET` | `/v1/admin/ontology-packs` | 초안 목록 |
| `GET` | `/v1/admin/ontology-packs/{id}` | 초안 상세 |

모두 관리자 전용(403), 조직 스코프.

### 3.7 절차 (운영)

```text
사용자 질문
  → RAG 검색 (조직·역할 ACL)
  → 모델 응답 (+ citations)
  → gap 감지
       ├─ 정상: 종료
       └─ 공백: JSONL 기록 + audit(knowledge.gap_detected)
                    ↓
             관리자 "지식 공백" 화면
                    ├─ 오탐/중요도 낮음 → 제외(dismissed)
                    └─ 클러스터 승인 → 꾸러미 초안(draft)
                              ↓
                    필요한 소스 확인 (문서 업로드 / DB 동기화 / 스키마 보강)
                              ↓
                    수용 질문으로 재질문 → citations 확인
                              ↓
                    (자동) 소스 업로드/DB 동기화 시
                       ├─ reviewed 꾸러미 재검증
                       └─ 미해결 공백 재평가(검색 1건이라도 성공하면 resolved)
                              ↓
                    커버리지 ≥ 80% → active, 원본 공백 resolved
```

### 3.8 저장·배포

| 항목 | 기본값 | Compose |
| --- | --- | --- |
| `GAP_STORE` | `/tmp/baryon-ax-gaps/gaps.jsonl` | `/data/gaps/gaps.jsonl` + `gaps` 볼륨 |
| `ONTOLOGY_STORE` | `/tmp/baryon-ax-ontology` | `/data/ontology` + `ontology` 볼륨 |

API 컨테이너는 비루트(uid 10001)로 실행되므로 이미지에서 두 디렉터리를 만들고 소유권을 맞춘다. 볼륨이 root 소유로 새로 생성되면 쓰기 실패(500)가 나므로, 볼륨 초기화 시 이미지 디렉터리 권한을 상속받도록 한다.

## 4. 검증된 동작 (2026-11-11)

- 단위·API 테스트 **96개 통과**, 이 중 공백/온톨로지 관련 **14개**
  - 감지 사유, 조사 제거, 중복 집계, 조직 격리, dismiss/convert
  - 클러스터 분리·병합, 소스 힌트 순위, 꾸러미 스키마, PackStore

- API 재시작 후에도 꾸러미·검증 결과 유지
- 관리자 화면 Playwright 확인: 요약 카드, 클러스터 카드, 공백 목록, 꾸러미 초안

## 6. 사례: "답 못 함"이 데이터 부족이 아니었던 경우

실제로 사용자가 문서를 37청크로 색인한 뒤 문서 제목으로 질문했지만 계속 "제공된 문서에서 찾지 못했습니다"가 나왔다.

- 원인: macOS가 문서·파일명을 **NFD(자모 분리)** 로 저장하고, 질의는 **NFC(완성형)** 로 들어옴. 기존 토크나이저가 `[가-힣]`만 매칭해 NFD 문서는 토큰이 0개였다.
- 조치: IR·저장·로드·질의에 NFKC 정규화, 제목 매칭 가산, 기존 문서는 재업로드 없이 정규화.
- 결과: 같은 질문이 4개 출처와 함께 정상 응답.

이 사례의 교훈은 분명하다. **공백 신호는 "무엇이 없는지"를 말해주지 않는다.** 따라서 다음 단계의 핵심은 공백을 곧바로 온톨로지로 바꾸는 것이 아니라, **원인을 분류하는 트리아지**다.

### 6.1 제안하는 원인 분류

| 원인 코드 | 판별 신호 | 조치 |
| --- | --- | --- |
| `missing_source` | 검색 0건 + 관련 문서 자체가 없음 | 문서/DB 수집, 온톨로지 꾸러미 |
| `retrieval_defect` | 문서는 있는데 검색 0건, 또는 인코딩·청킹·색인 불일치 | 파서·정규화·청킹·재색인 |
| `permission` | 같은 질문을 다른 역할은 성공 | ACL·조직 설정 |
| `question_ambiguous` | 짧고 지시어 위주("그거", "저번 건") | 되묻기 UX, 대화 문맥 |
| `model_behavior` | 근거가 있는데도 거절/모호 | 프롬프트·모델 교체, 평가 |
| `stale_source` | 문서는 있으나 갱신 전 내용 | 재수집·버전 관리 |

## 7. 미래 계획

### P0 — 트리아지와 루프의 최소 폐쇄 (1~2주)

| 항목 | 산출물 | 수용 기준 |
| --- | --- | --- |
| 원인 분류 | `cause` 필드 + 규칙(검색 결과 유무·문서 존재·권한 비교) | 공백 목록에서 원인별 필터 |
| 사용자 피드백 | 응답 하단 👍/👎 + 사유 선택 | 👎가 공백으로 유입, 오탐률 측정 가능 |
| 초안 편집 | 엔티티·관계·소스 편집/삭제, 버전 증가 | 편집 후 `status=reviewed` 저장 |
| 수용 질문 재실행 | 꾸러미 상세에서 "재검증" 버튼 + 소스 유입 시 자동 | ✅ 구현 |
| 커버리지 표시 | 꾸러미별 passed/total·부족 용어 | ✅ 구현 |
| 공백 대시보드 | 주간 공백 수·반복률·해결률 | 추세 확인 가능 |

### P1 — 자동 판정과 소스 연결 (3~6주)

| 항목 | 내용 |
| --- | --- |
| Answerability gate | 검색 점수·출처 커버리지·질문 유형으로 **사전** 답변 가능성 판정. 낮으면 안전 거절 + 공백 기록 |
| 근거 검증 | 답변 문장별 citation entailment 검사(소형 NLI/LLM judge). 근거 없는 문장 비율을 `unsupported_ratio`로 기록 |
| 임베딩 클러스터링 | 다국어 임베딩 + 동의어 정규화로 클러스터 품질 향상, 라벨 자동 명명 |
| DB 소스 매핑 | `ingest/db.py` introspection과 연결해 "이 꾸러미는 `erp.vendor_invoice.amount`가 필요"까지 제안 |
| 저장소 이전 | JSONL → Postgres(`kb_gap`, `kb_ontology_pack`), 인덱스·보존 정책 |
| 평가 하네스 | 꾸러미의 `acceptance_questions`를 골든셋으로 실행, 커버리지·인용률 리포트 |

### P2 — 폐쇄 루프와 조직 확장 (2~3개월)

| 항목 | 내용 |
| --- | --- |
| 재검증 정밀화 | citations 유무 + 엔티티 커버리지 + entailment를 결합해 오판 감소 |
| 커버리지 점수 | 도메인별 질문 커버리지, 공백 해결률, 평균 해결 시간 |
| Human-in-the-loop 라우팅 | 해결되지 않는 질문을 SME(전문가)에게 배정, 답변을 문서로 환류 |
| 온톨로지 거버넌스 | 꾸러미 소유자·승인자·버전·폐기, 조직 간 템플릿 공유(익명화) |
| 비용 대비 우선순위 | `빈도 × 업무 가치 × 소스 확보 난이도`로 로드맵 정렬 |
| 멀티테넌트 | 조직별 격리 유지, 플랫폼 관리자는 집계 지표만 조회 |

## 7.1 암묵지와 "질문 예산"

암묵지(tacit knowledge)는 문서에 없고 **사람에게 물어야만** 드러난다. 문제는 같은 질문이 반복된다는 것이다. 신규 구성원이 올 때마다, 부서가 바뀔 때마다 같은 것을 다시 묻는다.

이 루프가 줄이는 대상은 **반복되는 명시적 질문**이다.

| 단계 | 질문 예산에 미치는 효과 |
| --- | --- |
| 중복 집계 | 같은 질문이 몇 번, 누구에게 반복되는지 보인다 |
| 클러스터 | 개별 질문이 아니라 **공통 개념** 단위로 정리된다 |
| 온톨로지 꾸러미 | "무엇을 물어야 하는지"를 엔티티·관계·소스로 고정한다 |
| 자동 재검증 | 소스가 채워지면 같은 질문이 **더 이상 사람에게 가지 않는다** |
| 공백 자동 해소 | 꾸러미가 없어도 검색이 가능해진 질문은 `resolved`로 닫힌다 |
| SME 라우팅(P2) | 자동화로 닫히지 않는 잔여 암묵지만 전문가에게 보낸다 |

주의: 암묵지 전체를 온톨로지로 바꿀 수는 없다. 목표는 **"전문가에게 가는 질문의 수"를 줄이는 것**이지, 암묵지를 없애는 것이 아니다. 따라서 `질문 예산` 지표는 지식 커버리지와 함께 측정해야 한다.

### 질문 예산 지표

| 지표 | 정의 |
| --- | --- |
| `elicitation_questions` | 온보딩·프로젝트당 전문가에게 전달된 질문 수 |
| `repeat_question_rate` | 동일/유사 질문이 2회 이상 발생한 비율 |
| `auto_resolved_patterns` | `resolved`된 공백 패턴 수(사람 개입 없이 답변 가능해진 유형) |
| `escalation_rate` | 자동 해결 실패로 SME에게 간 비율 |
| `time_to_first_answer` | 최초 질문 → 근거 있는 첫 답변까지 |

## 8. 지표 정의

| 지표 | 정의 | 목표(예시) |
| --- | --- | --- |
| `gap_rate` | 공백 기록 응답 / 전체 응답 | 도메인별 기준선 설정 후 30% 감소 |
| `repeat_rate` | `occurrences > 1` 공백 비율 | 반복 질문은 우선 해결 |
| `resolution_rate` | `converted` 후 재검증 통과 / 전체 공백 | 3개월 내 50% |
| `time_to_resolve` | 첫 발생 → `converted` + 재검증 통과 | 중앙값 2주 |
| `dismiss_rate` | dismissed / 전체 공백 | 20% 이하(감지 정밀도 지표) |
| `unsupported_ratio` | 근거 없는 문장 / 전체 문장 | 5% 이하 |
| `coverage` | 골든 질문 중 citations 있는 비율 | 도메인별 80% |

## 9. 거버넌스·보안

- 공백에는 **질문 원문·답변 발췌**가 저장된다. PII가 포함될 수 있으므로 감사 로그와 동일한 보존·삭제·접근 정책을 적용한다.
- API는 관리자 전용이며 조직 스코프다. 클러스터·꾸러미도 동일하다.
- 꾸러미는 `draft → reviewed → active → retired` 상태를 갖고, 승인·폐기 모두 감사 이벤트를 남긴다.
- 모델 judge를 도입하면 프롬프트·출력이 외부로 나가지 않도록 온프레미스 모델만 사용한다.

## 10. 결정이 필요한 사항

1. **사전 필터 강도**: 너무 보수적이면 답할 수 있는 질문도 거절한다. 초기에는 기록만 하고(P0), 오탐률이 안정된 뒤 차단 비율을 올린다.
2. **공백 저장 기간**: 90일? 1년? 조직별 정책이 필요하다.
3. **꾸러미 승인 권한**: 조직 관리자 vs 지식 관리자 역할 분리 여부.
4. **임베딩 클러스터 도입 시점**: 현재 어휘 클러스터의 품질을 먼저 측정한 뒤 교체.
5. **피드백 수집 UI**: 👎만? 사유 선택까지? 사유가 있으면 트리아지 정확도가 크게 올라간다.
